FINDING (actionable, adapter-suite v2):

1. Every BEL in both captures terminates an OSC string. None is a "ring the
   bell" attention chunk. pi: 60/60; opencode: 5/5.
   The state engine flags BEL by scanning raw bytes for 0x07
   (crates/arreo-core/src/state/engine.rs:191 `if bytes.contains(&0x07)`),
   and with `bell_means_attention = true` (all three shipped adapters) a BEL
   with no prompt-shaped tail transitions straight to `blocked`
   (engine.rs:239). An idle pi TUI that renders one OSC 8 hyperlink therefore
   arms a false `blocked`; opencode's title/cursor-colour OSC does the same.
   The recorded T-0017 fixtures cannot catch this: they were captured in
   `--print`/text mode (fixtures/pi-*.pty, opencode*.pty), which emits no OSC.
   Fix belongs in adapter-suite v2 (parse-then-classify, or require a BEL that
   is NOT preceded by ESC ]): see the T-0075 follow-up "adapter v2: ESC-aware
   signal extraction".
2. Neither harness emits an OSC 9 / OSC 777 desktop notification or an OSC 133
   shell-integration mark from the TUI under probe. opencode exposes the
   opentui notification channel OSC 99 (probe only, no notification sent);
   pi has no notification channel visible in the capture — its attention
   signal is the terminal BEL only via the OSC terminator above.
3. opencode runs in the alternate screen (0x1b[?1049) from startup; pi does
   not (its "regular" TUI mode paints inline and scrolls). A pane-state reader
   that keys "am I in a full-screen app" off alt-screen will be right for
   opencode and wrong for pi in default `--tui-mode regular`.
4. Both enable bracketed paste; opencode asks for kitty keyboard protocol
   (0x1b[>…) and/or a `\x1b[?2031h` mode; pi enables a modifier-key mode
   (0x1b[>7u). Neither is a state signal on its own, but both break naive
   "paste the question text into the pane" quick-reply paths if the answer is
   sent without bracketed-paste framing.
