## Mutation: the pid cross-check (F1) is load-bearing

The check is 'claimed_pid' in adopt.rs: comparison of TIOCGSID against the claimed pid.
Mutation: delete the comparison (trust the claim, i.e. the pre-review behaviour).

```
$ cargo test -p arreo-core --test adopt          # WITH the check
test result: ok. 22 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out

$ # mutation: the comparison removed
$ cargo test -p arreo-core --test adopt          # trusted claim (pre-fix)
test adopt_refuses_a_pid_the_terminal_disagrees_with ... FAILED
thread panicked at crates/arreo-core/tests/adopt.rs:592
test result: FAILED. 21 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out
```

A mismatched pid is therefore refused only because of that comparison, and with it removed
the adoption succeeds — which is the defect (an arbitrary same-user pid becomes killable
through the pane API).

## Independent reproduction: ENOTTY on the master while the child is ALIVE

The reviewer's G1 claim is that 'tcgetsid failed' does not imply 'the child exited'.
Reproduced with a bare Python harness (no Arreo code) so the kernel fact stands alone:
openpty, fork, the child calls setsid() but never TIOCSCTTY, and keeps writing to the
terminal. Then TIOCGSID is issued on the master.

```
child state: S (R/S = alive, Z = exited)
TIOCGSID on MASTER -> errno 25 (Inappropriate ioctl for device)
still alive after the ioctl: S
bytes the live child wrote: b'tick\r\ntick\r\ntick\r\ntick'
```

So the child is in state S (alive, writing) while the master answers errno 25. A pty can
have no session with a live child, which is what makes 'tcgetsid failed -> the child
exited' an inference rather than an invariant.

Note: the reviewer's TIOCNOTTY variant also reproduces, but that ioctl delivers SIGHUP to
the foreground group, so the child dies unless it ignores SIGHUP — the clean form above
(never taking the controlling terminal at all) needs no signal handling and is the one
kept here.
