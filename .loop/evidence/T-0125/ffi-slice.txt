T-0125 — a real-daemon FFI slice: the check the battery cannot fake
===================================================================

`cargo xtask e2e --slice ffi` drives the product's own binaries — `arreo-relay
serve`, `arreo-server` and the `arreo` CLI — and reads a pane's metrics through
the **exported FFI surface**, twice on one session, against a machine whose
daemon keeps its session open after a verb. That property is what T-0114's
fixture could not see: the tree was green and wrong, and the proof lived in a
scratch crate under `target/` that nothing ran. This slice is that proof made
durable.

WHAT SHIPPED
------------
crates/arreo-core-ffi/tests/real_daemon.rs
    The driver: an `#[ignore]`d integration test of the FFI crate (so the check
    lives beside the boundary it drives, and `cargo test --workspace` stays a
    unit suite). It spawns the three binaries, writes the machine's identity the
    way `arreo pair` leaves it, issues the machine's certificate through the
    boundary, pins a **viewer** and an **owner** through the real
    `arreo devices issue`, spawns panes, and drives `relay_session_dial`,
    `machines`, `metrics_history` (three times on one session), `notify_act`,
    a wrong-but-valid pinned key, and an empty window.
xtask/src/ffi_slice.rs
    The slice: checks the binaries (SKIP, naming what is missing), runs the
    driver, echoes its evidence, and re-checks the numbers before it will call a
    run a PASS.
xtask/src/main.rs                       `Some("ffi") => ffi_slice::run(rest)`
docs/mobile.md                          the slice, under "What the gate does not prove"
AGENTS.md                               the command, beside the other slices

No `arreo-server`/`arreo-relay` code is linked anywhere in the harness: both are
spawned processes, and the driver is a test of the FFI crate, whose only
first-party dependency is `arreo-core` (the license-boundary gate in
`xtask/tests/workspace_deps.rs` keeps it that way).

WHERE THE TASK MET REALITY (the bends)
--------------------------------------
1. **The act door needs an owner, and the criterion pins a viewer.** The metrics
   session is a viewer's (that is what a phone is, and `Observe` is what a read
   needs). But `reply`/`skip` gate as `Verb::Send` and `kill` as `Verb::Kill`,
   and both need `Capability::Control` — owner only — so no viewer can *take* an
   act. The slice therefore pins **two** devices through the same real CLI: the
   viewer (whose session carries the p1, the pinning check, the empty window and
   the viewer's refusal) and an owner (whose session takes the reply). The act is
   one more verb on a session already held in both cases — on the owner's, read →
   act → read on one conversation; on the viewer's, the act arrives and the
   machine refuses it in its own words, which is itself the proof that the verb
   rode the reused conversation rather than a fresh handshake.
2. **"The gate's sentence" is the denial *record*, not the gate's sentence.**
   `docs/mobile.md` and T-0115's contract test say a viewer's act crosses as the
   gate's sentence. Against a real daemon it is `VerbDenial::Role`'s record:
   `device dev_… (viewer) denied: viewer may not Send (needs Control)`. The first
   run of this driver reddened on exactly that (it compared against
   `RoleError::Denied`'s `Display`). The fixture-based contract test never saw
   the wrapper, because the fixture answers with whatever it was told to answer —
   a small, sharp illustration of why this slice exists. The driver now builds
   the expected sentence from the core's own rules (`VerbDenial::Role` wrapping
   `role::check`), so both halves move with the core.
3. **The empty window has to be deterministic.** A pane spawned and read
   immediately races the daemon's 10 s sampler. The slice ends the window at the
   pane's own birth (`until_ms = spawned_ms`), which no tick can have sampled,
   and asserts the *history* path's answer: `step_ms = 10000` with
   `downshifted = true`. The unknown-pane path answers the ask back
   (`step_ms` = the ask, `downshifted = false`), so the pair is what
   distinguishes "no rows yet" from "no such pane".
4. **`xtask` depends on `arreo-server`, so a sibling's in-flight edit blocks
   `cargo xtask …` itself.** T-0117 was mid-flight in `arreo-core`/`arreo-server`
   for parts of this task (the `Message::NotifyPush` variant and its match arms),
   and `cargo xtask e2e --slice ffi` cannot build then — exit 101 from cargo, not
   from the slice. Two of the mutation captures therefore ran through the
   already-built `target/debug/xtask` (same source). The slice itself needs
   nothing but `target/debug/{arreo,arreo-server,arreo-relay}`; the driver is a
   test of the FFI crate, which does not depend on `arreo-server` at all, so
   `cargo test -p arreo-core-ffi --test real_daemon -- --ignored --nocapture`
   keeps working while `arreo-server` is red.
5. **`xtask` already links `arreo-server`** (the chaos slice does, and
   `workspace_deps.rs` exempts `xtask` as dev tooling). Nothing in *this* slice
   links either binary: the driver is a test of the FFI crate, which cannot link
   them, and the slice spawns them.

WHAT THIS SLICE DOES NOT PROVE
------------------------------
It proves the boundary against one real machine on loopback: protocol, the
conversation's lifetime, the pin, the empty window, the act door. It does not
prove WAN/NAT behaviour, a relay under load, or anything about the generated
Swift/Kotlin (that is `cargo xtask ffi --check`, whose SKIPs `docs/mobile.md`
records). It also runs only on unix, and says so rather than pretending: the
driver is `#![cfg(unix)]` and the runner SKIPs by name on other targets.
