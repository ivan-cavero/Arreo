T-0104 — UniFFI core bindings: one core, three UIs
==================================================

The client-relevant core gets a typed UniFFI surface so the Phase-3 mobile UIs are
written against a generated API rather than a Rust ABI. This is the one Phase-3 task
provable on this box, and the one the rest of Phase 3 depends on.

  src/{lib,errors,identity,pairing,relay,directory,codec,theme}.rs

THE DEPENDENCY DECISION (recorded before a line was written)
-----------------------------------------------------------
`uniffi` 0.32, chosen over: a hand-written C ABI (no type/error mapping — every function
is a manual edit in four places, and a struct change silently desynchronises them);
`cbindgen` (C headers only, no async, so Swift and Kotlin stay hand-written);
`flutter_rust_bridge` (targets a runtime ROADMAP §3.5 explicitly rejects: "no Flutter
runtime"). UniFFI generates Swift *and* Kotlin from one definition with typed errors,
records, enums and async — and it is what §3.5 already decided.

**The task's own premise was corrected before delegating.** It said "Kotlin bindings can
be compiled with a JDK if one is installed"; a JDK cannot compile Kotlin — `kotlinc` is a
separate compiler and this box has none (JDK 25 is present). The criterion was rewritten
rather than left as a claim that would have failed.

THE REVIEW, AND WHAT CHANGED
----------------------------
An independent reviewer returned **ship-with-follow-ups**: no p1, no data-loss or
auth-bypass defect, and it verified sound the three things I most wanted a second pair of
eyes on — the surface is client-shaped and leaks no server capability; the golden-symbol
assertion reads generated output and cannot pass vacuously (it checks both directions, and
the golden strings appear nowhere in the Rust source); the Kotlin "compile" branch is a real
`kotlinc` invocation, not a stub that reports PASS without compiling.

Nine of its ten findings are fixed here:

p2 the gate could not run off Linux — `CDYLIB` was the literal `libarreo_core_ffi.so`, so
   on the macOS runner (the platform that lifts the Swift SKIP) step 1 would fail after a
   successful build. Now `DLL_PREFIX`/`DLL_SUFFIX`.
p2 the Kotlin classpath was missing `kotlinx-coroutines-core` — uniffi emits
   `kotlinx.coroutines.*` imports whenever the interface has async functions (this surface's
   relay exports), and it is a separate Maven artifact, so the one non-SKIP compile path
   could not PASS even on a machine with everything the SKIP named. Now probed, added to the
   classpath, and named in the SKIP.
p2 **`device_cert_issue` bypassed the core's weak-key refusal.** This is the security half
   of the review. A small-order ed25519 point is not a key anybody can prove possession of —
   ed25519-dalek's own docs say a signature can be forged for almost any message under one —
   and `DeviceAuthority::issue` refuses it as `WeakKey`. This surface is the *only* issuing
   door a mobile UI has, and the key arrives from the peer
   (`PairingRequest.public_key`), so a malicious phone pushed a weak key through the one
   path that had no check: the FFI pinned an identity the CLI refuses. Fixed with the core's
   own predicate (`is_weak`) and the core's own sentence (carried from
   `AuthorityError::WeakKey`, never restated), plus a regression test and its control (a
   real key still issues, so the check refuses the *key*, not the call).
p3 a failed scratch-dir removal was swallowed, which could let a stale file satisfy the
   golden check — now a FAIL unless the error is `NotFound`.
p3 the summary printed `5 - skipped.len()` and so reported "3 pass, 2 skip" after five
   steps passed; now counted as they happen (the run above prints 5).
p3 `RootKeyHandle::sign` was an arbitrary-bytes signing oracle for the account's trust
   anchor, exported and called by nothing, and `docs/mobile.md` claimed the key "signs
   certificates and nothing else". Deleted, per the rule that everything in the tree exists
   because it is used — and the gate immediately caught the stale golden entry (mutation 2
   above).
p3 three doc corrections: the error-enum count (said ten, there are eight); the claim that
   CI runs this gate (`.github/workflows/ci.yml` has no `xtask ffi` step and is the user's
   file during T-0063 — the doc now says so plainly rather than implying a pre-merge job
   already tolerates the SKIPs); and the `cargo tree` evidence backing the proc-macro
   decision (askama/goblin/clap are *absent* from the normal tree; the one edge that is
   there, toml/fs-err/camino, arrives through the host-side `uniffi_macros` proc-macro).

**One finding is filed, not fixed — T-0113.** The reviewer is right that the shipped cdylib
carries SQLite (53 defined symbols matching `sqlite`; `rusqlite → libsqlite3-sys` in the
normal tree) and ~197 PTY symbols, none reachable from any export, in a product whose
ROADMAP §3.5 sets an explicit size discipline. I attempted the obvious fix —
`arreo-core = { default-features = false, features = ["transport"] }` — and **it does not
compile**: `arreo-core::mesh::resolve` calls `crate::store::rfc3339_ms` unconditionally
while `store` is gated behind `sqlite`. Making the core separable is a change to
`crates/arreo-core/src/**`, which is **outside this task's fence**, so the attempt was
reverted with the reason recorded in the manifest and the work filed as T-0113 (with the
rule that its fix is measured by symbol count, not asserted). The numbers in
`docs/mobile.md` are my own measurements, and they disagree with the reviewer's (53 vs its
15) — the doc states the exact command so the figure is reproducible rather than borrowed.

VERIFIED SOUND BY THE REVIEWER (no change needed)
-------------------------------------------------
- The exported surface is client-shaped; no path, no child process, no PTY/daemon/store
  capability; the codec is a pure transform so the daemon's role gate still decides every verb.
- No `Result<_, String>` in the surface; the sentences are the core's own `Display`, so they
  are the CLI's by construction.
- The contract test drives the exported items; its only `arreo_core` references are
  server-side vocabulary the test-local mailbox/relay need, never a client API underneath.
- All 38 new vet exemptions exist in `Cargo.lock` and none is unused.
