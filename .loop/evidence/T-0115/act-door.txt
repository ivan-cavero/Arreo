THE DESIGN, AND THE TWO THINGS IT DELIBERATELY DOES NOT DO
----------------------------------------------------------
All three actions cross, because the machine's gate treats them differently: `reply` sends
`text + "\n"` through the *same audited send path* a direct send takes (same trust gate,
same secret scan, same redaction), `skip` writes no pane bytes at all, `kill` ends the pane
through the pane-kill path. The gate: `reply`/`skip` are `Verb::Send`, `kill` is `Verb::Kill`.

**Every refusal is the machine's own sentence, carried byte for byte** into
`SessionFfiError::Daemon`, exactly as a metrics refusal crosses — "the pane has exited" (the
pinned sentence the CLI keys its exit code on), "cannot reply: the pane is not asking
(state=…)", "reply text is too long: N bytes, the bound is 4096".

Two things the boundary does **not** do, both for the same reason:

- **No client-side reply-bound check.** The daemon refuses an over-long reply with its own
  sentence *and records the refusal as an audit row*. A courtesy check here would need a
  second copy of that sentence — the drift the typed-error rule exists to prevent — and
  would hide the refusal from the log. One definition (`arreo_core::notify::MAX_REPLY_BYTES`,
  which the daemon's refusal names and which the test drives the over-bound case through).
- **No client-side capability check.** A viewer's act is *sent*, and the daemon refuses it, so
  the sentence the phone shows is one the machine actually said. A boundary that decided
  locally would show the operator a rule the machine never applied — which is exactly what
  the viewer test's last assertion pins ("the verb reached the machine").

**A phone that answers notifications is an owner.** `reply`/`skip` gate as `Verb::Send` and
`kill` as `Verb::Kill`, and both need `Capability::Control`, which only the owner role holds.
A viewer can read panes, metrics and the directory, and cannot answer. That is T-0046's
intended split, and `docs/mobile.md` states it where a pairing screen would need it.

T-0114's LESSON, APPLIED
------------------------
T-0114 shipped green-and-wrong because its fixture closed its session after each answer,
hiding the behaviour a real daemon has. This verb rides the **same** cached conversation, so
the test was written against the rewritten fixture (one conversation, N verbs) and asserts
**seven verbs on one handshake**: a metrics read first, then `reply` (taken), `skip` (taken),
the pane-exited refusal, the not-asking refusal, the over-bound refusal, and a `kill`. A read
and five acts on one conversation — the cache is per peer, not per verb.

The refusal sentences in the fixture are **built by the daemon's own rules**
(`notify::state_word`, `notify::MAX_REPLY_BYTES`, the pinned `notify::PANE_EXITED`) rather
than typed as literals, so the test asserts the crossing rather than a second spelling of it.
The viewer test asks the core's own policy for the denial sentence
(`SessionAuth::authorize`'s `denial.to_string()`) for the same reason.
