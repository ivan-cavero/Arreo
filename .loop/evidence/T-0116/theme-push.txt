phone does not have and a browser will not. The server can now send one.

THE WIRE SHAPE — THE DESIGN PINNED BEFORE DISPATCH, AND WHY
-----------------------------------------------------------
`theme` → `theme_reply`. The reply carries `ThemeTokens { name, variant, tokens }` with
every value a **literal color in the theme file's own spelling** (`#rrggbb`, a 0–255
index, `none`) — resolved, never a `defs` reference, and never the on-disk document.

The first draft of this task's criterion said "the same shape `brand.rs` already parses".
Probing the engine showed that names the wrong format, and the difference decides the
design: there are two JSON formats and neither is the right payload. `theme/schema.rs`'s
`RawTheme` is the on-disk file (`$schema`, `defs` with named references, per-token
per-variant values), and `theme/brand.rs` parses the brand document, which is a design
artifact rather than a user theme. Sending either would push the `defs` resolution, the
token-name validation and the per-variant unwrapping onto every client — so a phone and a
browser would each carry the resolver and each be a place it could diverge. The engine
already separates those steps (`schema::resolve` → `BTreeMap<String, Color>` →
`Theme::new`), and **that resolved map is what crosses**.

It is also what makes depth fallback a *client-side* property, which is the criterion that
would otherwise be lost by moving resolution to the server: the same document degrades
differently on a 16-colour terminal and a truecolor one.

Answers, per the criteria: an unknown name is a **typed refusal naming the name** and
listing the built-ins; an unconfigured machine answers with the built-in default (the
default is a working answer, not a failure); the verb gates as `Verb::Read` and writes no
audit row (reads are deliberately unaudited); `size_of::<Message>() == 112` still holds
(the pinned budget — `ThemeReply` carries `ThemeTokens` inline).

INTEGRATION WORK THE PLANNER DID (not the worker's)
---------------------------------------------------
1. **The FFI codec mirror.** `WireMessage` mirrors `Message` variant for variant and
   `from_core`'s match is exhaustive, so T-0116's two new variants were a **compile error**
   in `crates/arreo-core-ffi/src/codec.rs`. That tripwire is a feature — it forces a
   decision instead of letting the mirror fall behind — so it was honoured rather than
   worked around: `WireThemeTokens` + the two variants + both match arms, with the theme
   spelled through the core's own `Color`/`Display` (never a format string written in the
   FFI). `ThemeToken::color_as_text` gives callers that spelling without re-inventing it.
2. **`tests/theme_mirror.rs`** — the exhaustive match catches a *missing* variant, not a
   *wrong* mapping, so the round trip is asserted: request and reply encode → decode
   unchanged, every token present with its color, and the values are the file's own
   spelling (`["#121418", "10", "none"]`). Mutation: the mirror drops the variant
   (`variant: Variant::Dark` unconditionally) → RED with
   `left: Theme { … variant: Dark }, right: Theme { … variant: Light }`. The test was kept
   in its own file so the two units could be committed as separate deliverables.
3. **Three clippy findings** the workers were (correctly) told not to chase: `&PathBuf` in
   `theme_push.rs`, a `filter_map` that had become a `map` in the mirror, and a
   single-pattern `match` in `theme_slice.rs`.
