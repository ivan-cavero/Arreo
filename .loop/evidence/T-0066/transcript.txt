T-0066 — the exit criterion, exercised (final)
==============================================

Timed, from empty dirs, following only named steps. 8 s to the last step.

## What works
  - relay + account registration (once the root PUBLIC key is used)
  - machine A admits itself: a certificate is issued and saved (3.5 s)

## What fails, in order

1. The account root public key is not discoverable.
   'arreo devices list' prints 'root 17d0a47fbfc70f63...' - TRUNCATED.
   identity/root.key holds the SECRET seed, so registering it fails later with
   'certificate signature does not verify under the root key' - a confusing,
   late, and dangerous-looking failure. The full value exists only in
   'devices list --json' ({"root": ...}), which no document mentions for this.

2. Even with the account registered from this machine's own root public key,
   the daemon's relay registration is REFUSED:
     arreo-server: relay registration failed: the peer's certificate does not
     authorize it: certificate signature does not verify under the root key
   The daemon reports the same root the account was registered with
   (b7982e04edd07dc1...), so this is not a path mismatch. The self-admitted
   certificate is not verifiable against the account root. Diagnosis continues;
   the mesh slice's certs (issued in-process via DeviceCert::issue with the
   account root) DO verify, so the difference is in the pairing issuance path.

3. The relay's handshake budget masks all of the above.
   Once a machine retries, 127.0.0.1 exceeds 3 handshakes/10 s and the error
   becomes 'the server refused to accept a new connection' - which reads as a
   network problem, not a certificate problem. On loopback (one IP) a stranger
   testing the flow hits this immediately.

## Verdict
The exit criterion FAILS, and the failure is in the product, not only the docs.
Script: exit-criterion.sh (run it to reproduce).
